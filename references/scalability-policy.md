# Scalability Policy

本文件定义 wiki 内容增长后，如何避免上下文过长导致系统不可用。

## 目标

- 控制单页体积，避免一次读写超出模型有效上下文。
- 保持页面可追溯，不因拆分丢失证据链。
- 让 `query`、`lint` 在大规模知识库下仍可稳定运行。

## 风险信号

运行阈值统一读取 `schema.json` 的 `limits`。出现以下任一信号时进入扩容治理阶段：

- 单页行数、字节数或二级标题数超过对应阈值。
- 同类查询反复需要跨多批读取，且多数候选无关或重复；超过一批本身不表示必须重构。
- `lint` 单次扫描页面数超过批次阈值。

## 分层治理策略

### 场景 1：单页过长

- 拆分为「主页面 + 子页面」结构。
- 主页面保留：定义、导航、关键结论。
- 细节迁移到子页面（如 `concepts/foo-details.md`、`concepts/foo-cases.md`）。
- 主页面必须包含子页面索引与双向链接。

### 场景 2：主题过大

- 按子主题建立聚合页（topic hub），例如 `wiki/hubs/<topic>.md`。
- 聚合页只做目录与关系图，不重复全文内容。
- `query` 先读 hub，再按需读取子页。

### 场景 3：历史内容堆积

- 对已稳定内容做「历史归档页」，保留结论与来源。
- 主页面只保留当前有效版本与归档入口。
- 归档页必须带时间戳和来源快照。

## 写入约束

- 禁止为压缩长度而删除来源引用。
- 拆分后 `wiki/index.md` 必须新增子页面条目。
- 拆分、归档的授权遵循 `guardrails.md`，完成后执行 `lint-policy.md` 的共用写入收尾。
- 素材与来源字段的维护边界见 `okf-frontmatter.md`。

## Query 运行策略

搜索、分批和继续读取统一遵循 `query-policy.md`。多批查询优先使用搜索会话复用候选；index、hub 与 overview 用于导航，正文搜索负责兜底。

## Lint 运行策略

- CLI 执行确定性检查，使用 `--lint-files` 或 `--lint-dirs` 缩小报告与修复范围；仍需建立全库来源和入链关系，同一次调用复用读取结果。
- 语义复核由 Agent 按主题执行，范围与要求见 `lint-policy.md`。写后检查不额外触发全库语义巡检。
- 当前没有独立 fast/deep 开关，也不生成「过长页面 Top N」；脚本逐项报告超限页面，Agent 根据实际体积和查询负担建议治理。

## 提炼运行策略

按 `synthesis-policy.md` 对变更、依赖和命中候选进行增量复核，首次或显式整理才全库回扫。工具默认只输出批次明细，日志检查点仅追加新指纹，避免周期性重复保存全量状态。

## 阈值来源

所有阈值只在 `schema.json` 的 `limits` 定义。策略文件和脚本不得复制数值常量。

单页超阈值时建议拆分；简短但完整的页面不因字数少而要求扩写。无需为每次微小修改额外生成体积报告。
